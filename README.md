# carcache

A tiny, local, reusable CLI for comparing used-car listings saved from **mobile.de**.

## Why this exists

Reading a listing PDF with a vision model is expensive and hits per-session image
limits. But the extracted facts are tiny and stable. So `carcache` extracts each listing
**once**, stores it in `cars.json` keyed by the mobile.de listing id, and runs every
comparison / ranking / filter off that JSON — **never re-reading a PDF whose id is already
stored.**

- `carcache.py` (the core) is Python **3.11+**, standard library only, no dependencies.
- `extract.py` (optional helper) uses `pypdf` to read a PDF's text layer — **zero image
  cost**. `pip install pypdf` to use it.
- Tests use `pytest` (dev-only).

## Files & folders

| path | role |
|------|------|
| `cars.json` | the store — one record per mobile.de id |
| `profile.json` | **your** fixed search criteria + scoring config (editable) |
| `carcache.py` | the CLI (stdlib only) |
| `extract.py` | optional: PDF text → record skeleton, no vision (needs `pypdf`) |
| `inbox/` | drop new listing PDFs here |
| `processed/` | PDFs are auto-moved here (renamed `<id>.pdf`) once handled |
| `report.md` / `report.html` | generated by `report` (Markdown + a visual HTML report) |
| `test_carcache.py` | pytest suite |

## Setup

The `carcache.py` CLI is stdlib-only — clone and run. For `extract.py` (PDF text) and the
tests, create the venv once:

```bash
make setup        # python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
make test         # run the suite
make help         # list all make targets
```

## The workflow (drop → intake → extract → add)

1. **Drop** new mobile.de PDFs into `inbox/` (any filename).
2. **Intake** — dedupe by id, with zero image cost:
   ```bash
   python3 carcache.py intake
   ```
   - PDFs whose id is **already cached** are skipped and moved to `processed/<id>.pdf`.
   - **New** PDFs are renamed to `inbox/<id>.pdf` and listed with a ready-made `add`
     command. Use `--force` to re-extract an already-cached id.
3. **Extract** each NEW listing (pick one):
   - **Text layer, no image cost (recommended):** `python3 extract.py inbox/<id>.pdf --json <id>.json`.
     Every labelled row on the page is parsed — nothing is left to fill in by hand.
     Batch mode does every new inbox PDF at once: `python3 extract.py --inbox` (writes one
     `<id>.json` per new listing, skipping cached ids).
   - **Vision:** if the PDF is image-only, read its pages with a vision model instead
     (needs `poppler` installed so the pages can be rendered).
4. **Add** it — this archives the PDF and marks the listing live:
   ```bash
   python3 carcache.py add <id> --file <id>.json --pdf inbox/<id>.pdf
   ```
5. **Rank / report** across the whole set at no image cost for anything already stored.

### Adding a car by hand

Get the id from the URL footer (`…/details.html?id=459081695`). Check the cache first —
`python3 carcache.py show 459081695` — if it prints a record, it's already cached, stop.
Otherwise extract and `add` as above. `python3 carcache.py pdf-id <file>` prints the id a
PDF contains without touching the store.

## Commands

```
add <id> --file F [--pdf P] [--force]   upsert one listing; --pdf archives it to processed/
show <id>                               print one record
list [--stale-days N]                   compact table of all cars
filter --<field> <value> …              query the store (repeatable)
rank [ids…] [--stale-days N] [--refresh] [--sensitivity [N]]   score, rank + TCO (+ influence table; --sensitivity adds Monte-Carlo weight robustness)
report [ids…] [--output F] [--refresh]  write report.md + report.html (visual)
intake [--force]                        scan inbox/, dedupe by id, archive cached, flag new
refresh [ids…]                          re-check availability on mobile.de (network)
set-active <id> live|sold|unknown       record availability manually
check-urls [ids…] [--unchecked|--stale-days N] [--json]   worklist for a browser check
apply-availability --file results.json  batch-apply {"<id>": "live|sold|unknown"}
apply-parkplatz --file park.json        update price + availability from a mobile.de parkplatz scrape
status                                  which stored cars drifted from current logic/profile
recompute                               refresh stored score/TCO snapshots
pdf-id <file>                           print the mobile.de id found in a PDF
```

`extract.py` (needs `pypdf`): `extract.py <pdf> [--json OUT]` · `extract.py --inbox [--force]`
(batch every new inbox PDF) · `extract.py --reprocess [--all] [--ids …]` (rebuild records
from `processed/` PDFs) · `extract.py --verify` (independently audit stored records against
their archived PDFs).

Global options (before the subcommand): `--store cars.json`, `--profile profile.json`.

### `add` — the guard that prevents re-processing

An already-cached id is **skipped** and nothing is written, unless you pass `--force`.
Missing fields are filled with `null` (lists with `[]`); a freshly added listing is marked
`active: true` with today's `last_checked`, and `--pdf` moves the source into
`processed/<id>.pdf`.

### `filter` — repeatable field queries

```bash
python3 carcache.py filter --towbar fitted_fixed --max-km 110000 --adaptive_cruise true
python3 carcache.py filter --make Ford --min-year 2020
```

- **Equality** on any schema field; strings match case-insensitively, `true`/`false`/`null`
  are typed, a bare `--service_history` means `true`.
- **Ranges:** `--min-km` `--max-km` · `--min-price` `--max-price` · `--min-year` `--max-year`
  · `--min-ps` `--max-ps` · `--min-owners` `--max-owners` · `--max-km-yr`.

### `rank`

Ranked table (score + a **separate** TCO/yr column) then a per-criterion 0–10 breakdown.
An `act` column shows availability (`live` / `SOLD` / `?`); cars marked SOLD are also listed
as a warning. `*` on a TCO means consumption was estimated. `--refresh` re-checks
availability first (network); `--stale-days N` marks records fetched more than N days ago.

## Availability (and an honest caveat)

Every record carries `active` (true/false/null), `last_checked`, and `listing_url`.

- `refresh` pings each listing URL and updates `active` — but **only flips a car to SOLD on
  a confident removal signal** (HTTP 404/410 or a "nicht mehr verfügbar" page). Newly-sold
  cars are reported as a message; `rank`/`report` surface them too.
- **mobile.de bot-blocks automated requests from servers (HTTP 403)** — both this tool and
  most fetchers get blocked regardless of whether a listing is live or gone. So `refresh`
  will usually report **`unknown` (unverified)** rather than lie. When that happens, record
  the truth yourself:
  ```bash
  python3 carcache.py set-active 459081695 sold      # or: live | unknown
  ```
  A reliable automated check needs a real browser session (e.g. driving Chrome); the tool
  deliberately does not pretend a 403 means "sold".

**Reliable check via a real browser (past the 403).** With the Claude for Chrome extension
connected, Claude Code can verify listings and write the results back:

```bash
python3 carcache.py check-urls --unchecked --json     # worklist of {id, url}
#  → Claude opens each url in Chrome, reads live vs "nicht mehr verfügbar",
#    writes results.json = {"<id>": "live|sold|unknown", ...}
python3 carcache.py apply-availability --file results.json
```

See `CLAUDE.md` for the exact agent procedure.

## Freshness

`price_eur`, `price_rating` and availability are **re-checkable** over time; static fields
(year, km, engine, equipment) never need re-reading. `list`/`rank --stale-days N` mark any
record fetched more than *N* days ago as `STALE`. Nothing is auto-deleted.

## Versioning & recalculation

Change what you're searching for, or how a feature is computed, and `carcache` can tell you
which stored cars are out of date. Two independent stamps:

| you change… | detect with | fix with |
|-------------|-------------|----------|
| extraction code or the record schema (bump `EXTRACT_VERSION`) | `status` → `extract` = STALE | `extract.py --reprocess` — rebuilds each car's mechanical fields from its `processed/<id>.pdf` (your reviewed judgment fields are preserved) |
| a weight, the TCO formula (bump `SCORING_VERSION`), or anything in `profile.json` | `status` → `scores` = STALE | `carcache.py recompute` — refreshes the stored score/TCO snapshot |

```bash
python3 carcache.py status       # e.g. "9 car(s) score-STALE … → carcache.py recompute"
python3 carcache.py recompute    # re-score the whole set at the current version + profile
python3 extract.py --reprocess   # rebuild extract-stale cars from their archived PDFs
```

`rank`/`report` **always** compute live from the current profile + logic, so rankings are
never stale — the stored `computed` snapshot only powers `status` (drift detection) and
keeps a versioned copy in the JSON. Each record carries `extract_version`; the profile is
tracked by a short fingerprint (a hash of weights, TCO config, and maps).

## The scoring model (`profile.json`)

**There are no hard filters.** Listings reach the store from your own mobile.de search, so they
already match your criteria — every stored car is scored and ranked. (`filter` is a separate
query command for slicing the store by hand; it does not affect ranking.) The one exclusion is
a listing marked `superseded_by`, i.e. the dealer's older ad for a car that is listed again
under a newer id — see `dedupe`.

**Weighted criteria (each 0–10; weights sum to 1.0):**

| criterion | weight | source |
|-----------|:------:|--------|
| reliability | 0.19 | **derived** from `model_reliability_basis` (TÜV Mängelquote + ADAC Pannen), age-projected per listing and normalised vs a frozen market reference — see below |
| condition | 0.19 | **derived**: reported damage/defects + history (see below) |
| equipment_fit | 0.15 | **derived**: weighted `wishlist` share (towbar counts only if *fitted*) blended with registration-year recency (`equipment` block) |
| autobahn | 0.11 | **derived** from power_ps + segment guess (override via `autobahn.map`) |
| **cost** | **0.21** | **composite** of asking price + mobile.de price rating + annual **cash** running cost (`cost` block) — see below |
| mileage | 0.10 | **derived**: absolute odometer curve (`mileage.best_km`→10, `worst_km`→0, clamped) |
| location | 0.05 | **derived**: absolute travel-time curve from `location.origin` (`best_minutes`→10, `worst_minutes`→0); data from `carcache.py travel`. Weight deliberately small: visiting is a one-time trip, not ownership, and this criterion's wide spread makes it punch above its weight |

Maps resolve by the most specific key whose tokens all appear in `"make model"` (so
`opel insignia` beats `opel`). **Every criterion is an absolute curve or a per-listing
lookup** (`mileage`: `best_km` 30,000 → 10, `worst_km` 180,000 → 0; `location`:
`best_minutes` 90 → 10, `worst_minutes` 480 → 0; `cost.running`: €1,800/yr → 10,
€3,600/yr → 0), so a car's scores and total never change when you rank a subset — a test
guards this. `equipment_fit` = `wishlist_weight` (0.7) × wishlist share + `year_weight` (0.3)
× year recency (`year_worst`→0, `year_best`→10). The year term is a deliberate preference: a
newer car's kit is newer-generation even with identical boxes ticked, so age counts here as
well as in reliability — an accepted, documented overlap (`year_weight 0` = pure wishlist).
Don't wishlist options your search already guarantees — they add a constant, not
discrimination.

**Is the ranking trustworthy?** `rank` prints (and the report includes) two diagnostics:

- **Criterion influence** — weight × observed spread (sd) of each criterion's scores. A
  criterion every car scores 8–10 on cannot rank anyone whatever its weight; compare the
  `share` column to the nominal weight when retuning `weights`.
- **Weight sensitivity** (`rank --sensitivity`, also always in the report) — hundreds of
  re-rankings with every weight independently perturbed ±30% (deterministic seed). A car
  with P(#1) = 100% wins under every plausible weighting: the decision does not hinge on
  the exact numbers in `weights`.

**Location** answers "how annoying is it to go see this car". Run `carcache.py travel` once: it
geocodes each dealer town (Nominatim) and routes from `location.origin` (OSRM), storing
`travel_minutes`/`travel_km`/`travel_mode` on the record, so `rank`/`report` never hit the
network. Preference order is public transport → car time → car distance → straight-line;
public transport is currently unavailable (the free DB endpoint 503s), so records hold real
driving times. With `best_minutes` 90, Berlin and Brandenburg both score 10.

**Wishlist (`equipment_fit`)** is `{option: weight}` — the score is the weighted share of
desired options present (see `profile.json` for the current set and weights). Add options or
retune freely, but don't list anything every candidate has — your mobile.de search already
guarantees it, so it would shift every car by the same constant (that's why `carplay` and
`heated_seats` were removed).

**Condition** is a single 0–10 score from **current reported condition + history**. It starts
at 10 and subtracts for: a declared accident (`unfallfrei_declared` false) or undeclared
status, extra owners, missing service history, missing TÜV, and **disclosed defects at the
severity the reviewer stated** (`findings`). A *major disclosed mechanical defect* (coolant/oil
leak, head gasket, rust-through, engine/gearbox damage) is penalised heavily — so a car with
reported leakage cannot score high — while minor cautions are small and capped, and `note`
findings never penalise. Penalties live in `profile.json` → `condition`.

Two rules keep it honest:

- **An accident is charged once.** If the seller *declared* the damage, the declaration carries
  the penalty and any `accident` finding restating it is ignored. If the seller declared the car
  accident-free but the description admits damage, the finding is graded on its own merits —
  cosmetic is `minor`, structural is `major` — and that is the only way such damage scores.
- **`inconsistency` findings never touch Condition.** They describe a contradiction in the
  *advert*; a typo does not make the car worse. They are shown, and scored 0.

**Cost** is a **composite** of three things a single €/yr figure cannot separate — a cheap car
can still be poor value, and a well-priced car can still be expensive to run. Each part is an
absolute 0–10 (`cost.weights` are relative and retunable):

| component | 0–10 from |
|-----------|-----------|
| asking price | absolute curve, `cost.price.best_eur` → 10, `worst_eur` → 0, clamped |
| price rating | mobile.de's own verdict: `Sehr guter Preis` 10 · `Guter Preis` 7.5 · `Fairer Preis` 5 · `Erhöhter Preis` 2.5 · `Hoher Preis` 0; **unrated → 5** (neutral — silence is not a bad price) |
| running cost (cash) | annual TCO **minus depreciation**, absolute curve: `cost.running.best_eur_yr` → 10, `worst_eur_yr` → 0, clamped |

**Depreciation is displayed but not scored.** It is estimated *from the asking price*, and the
asking price already has its own third — scoring depreciation too charged the same euros twice
(a €15k car lost on the price curve AND was billed ~€300/yr more depreciation than a €10k car).
It also pulled the hand-set `brand_retention_adj` priors into the score. The full TCO/yr
including depreciation still appears everywhere as information.

Tune the curves and the rating map in `profile.json` → `cost`. The report's *Cost of ownership*
section shows all three parts per car, and the running cost broken down by component.

**TCO (annual)** follows the ADAC Autokosten structure — a sum of components, not a flat fee:

| component | how it's estimated |
|-----------|--------------------|
| depreciation | value loss from the current price over a 5-yr hold: `price·(1−r⁵)/5`, retention `r` rising with age and by resale-strong brand — usually the biggest cost |
| petrol | `consumption/100 · annual_km · fuel_price`, using **measured real-world consumption** where available (`model_consumption`), else the listing's WLTP, else CO₂, else a default |
| electricity | **plug-in hybrids only** — `electric_share` of the km at `kwh_per_100km · electricity_price` |
| maintenance | ADAC Werkstatt + tyres: per-segment base × an age uplift |
| insurance | per-segment base + a surcharge for high power |
| Kfz-Steuer | **computed exactly** (displacement + CO₂ + fuel + reg-year, tiered for 2021+) |
| HU | flat ~€65/yr |

All constants live in `profile.json` → `tco`. Depreciation, maintenance and insurance are
estimates anchored to ADAC reference figures; the road tax is exact.

> **Plug-in hybrids.** A PHEV's WLTP figure (e.g. 1.6 l/100km) is a *blended* number that assumes
> you charge and drive mostly electric — and it excludes the electricity you buy. Taken literally it
> made a PHEV look like ~€180/yr to run. So for a detected plug-in (`tco.phev`) the WLTP litres are
> ignored: `electric_share` of the km run on grid electricity and the rest on the engine at
> `petrol_l100_engine`, giving a separate **electricity** component. Full and mild hybrids have no
> plug — their stated consumption is real petrol burn and is used as-is.

## Data sources

- **Reliability** is **computed** from real **per-cell** figures in `model_reliability_basis` — not
  a hand-set number. Each model holds `tuv_by_age` (TÜV Mängelquote per age band) and `adac_by_year`
  (ADAC breakdowns/1000 per registration year). For a listing, the **TÜV cell for its age band** and
  the **ADAC cell for its reg year** are looked up directly (no projection), each mapped to 0–10
  against a frozen market reference (cell = mean → 5, ±2σ → 10/0), averaged 50/50. So an older listing
  of the same model scores lower, and the best car nears 10 only if it's genuinely far better than the
  market. The **ADAC values are the official ADAC Pannenstatistik 2025 per-year cells** (e.g. VW Golf
  2.6→10.5 across build years 2022→2015; Opel Insignia 17.2→40.9; Renault Mégane 1.8→35.0); models
  absent from the statistic (Hyundai i40, Kia Optima — discontinued) are scored on TÜV alone. **TÜV
  cells are the official per-model "erhebliche Mängel" rates by age band from the AUTO BILD TÜV-Report
  2026**, extracted from the magazine PDF's text layer by `sources/extract_tuv.py` (each cell records
  its `tuv_source` page). Models the 2026 report doesn't cover (Hyundai i40, Kia Optima, Renault
  Talisman) keep modelled figures or fall back. Config + rationale: `profile.json` →
  `reliability_model` and `_sources`.
- **Condition** blends the listing's reported damage/defects (severity-classified) with
  history. **`comfort` and `looks` were removed** — neither can be extracted from a listing in
  a data-driven way (comfort had no ADAC/TÜV-equivalent statistic, only a subjective rubric).
- **TCO**: ADAC Autokosten component model; Kfz-Steuer per the German formula (§8 KraftStG).

- **Safety (Euro NCAP)** is **informational, deliberately not scored** (`profile.json` →
  `model_safety`, shown in the report). Every model in the catalogue is 5-star, and NCAP
  percentage scores are **not comparable across protocol years** — the test gets stricter every
  few years, so the Focus's 85% (2018 protocol) is not worse than the Golf's 94% (2012
  protocol). Scoring the raw percentage would rank cars by test vintage, not safety. Values
  verified against euroncap.com per-model result pages.

Sources: [TÜV Report](https://www.tuvsud.com/de-de/publikationen/tuev-report/maengelzwerge-und-fehlerriesen) ·
[ADAC Pannenstatistik](https://www.adac.de/rund-ums-fahrzeug/unfall-schaden-panne/adac-pannenstatistik-2026/) ·
[ADAC Autokosten](https://www.adac.de/rund-ums-fahrzeug/auto-kaufen-verkaufen/autokosten/) ·
[ADAC Kfz-Steuer-Rechner](https://www.adac.de/rund-ums-fahrzeug/auto-kaufen-verkaufen/kfz-steuer/kfz-steuer-rechner/) ·
[Euro NCAP](https://www.euroncap.com/en/ratings-rewards/latest-safety-ratings/)

## Schema (one record per id)

Every field below is owned by exactly one writer. **Parsed** fields come from a labelled row in
the PDF and are rebuilt by `extract.py --reprocess`; **LLM** fields come from the seller's
free-text description and are written only by `review.py`; the rest is managed metadata. The two
sets are disjoint, and `review.apply_to_record()` refuses to cross the line.

**Parsed** (`carcache.PARSED_FIELDS`) — `model` · `make` · `variant` · `body` · `price_eur` ·
`price_rating` (sehr_gut|gut|fair|erhoeht) · `first_reg` "MM/YYYY" · `km` · `owners` ·
`power_ps` · `fuel` (Benzin|Hybrid-Benzin|PHEV|Diesel) · `gearbox` · `displacement_cm3` ·
`consumption_l100` · `co2_gkm` · `emission_class` · `unfallfrei_declared` (true|false|null — the
seller's `Fahrzeugzustand` tick-box, **not** a verdict on the car) · `tuv` · `service_history` ·
`climate` · `adaptive_cruise` · `cruise` · `carplay` · `navi` · `heated_seats` · `heated_wheel` ·
`standheizung` · `variable_floor` · `roof_window` · `blind_spot` · `rear_camera` · `keyless` ·
`towbar` (fitted_fixed|fitted_swivel|capable|prep|null) · `towing_braked_kg` · `parking` ·
`warranty` (bool — the Garantie tick-box) · `dealer` · `dealer_rating` · `location`

**LLM** (`carcache.LLM_FIELDS`) — `findings[]` (`{severity, category, summary, evidence}`) ·
`options_from_prose[]` (wishlist keys the seller describes but did not tick) ·
`notable_options[]` · `review_summary` · `reviewed_by` · `reviewed_at` · `reviewed_source` ·
`review_prompt_sha`

**Managed** — `id` (key) · `source_pdf` · `superseded_by` (set by `dedupe`; excluded from
rank/report) · `travel_minutes` · `travel_km` · `travel_mode` · `fetched_date` · `listing_url` ·
`active` (true|false|null) · `last_checked` · `extract_version` · `computed` (stored score/TCO
snapshot, managed by `recompute`)
